# Community data and media setup for review

No database or Storage changes have been applied. The review SQL is [docs/sql/community-posts-storage-review.sql](sql/community-posts-storage-review.sql), separate from migration history. The transient Supabase CLI could not create a migration because startup tried to create `/home/agent/.supabase` on the read-only filesystem; a bounded configuration retry had the same result. No credentials or remote database access were requested.

## Review and application order

1. Review the SQL against the intended project's schema and policies. It expects existing `public.clients` with `auth_user_id`, `program`, `access`, `active`, `verified_purchase`, and `subscription_ends_at DATE`; the captured schema has that date type. The UTC expiry boundary matches existing member-access code. Confirm `authenticated` can select its own client under existing RLS. Keep `community_private` out of the Data API's exposed schemas.
2. Generate a migration through the installed Supabase CLI after approval; copy the reviewed SQL into it and validate on an isolated Supabase instance. The new table DDL deliberately fails if the proposed community tables already exist, requiring fresh review instead of overwriting them. Verify PostgreSQL grants, Storage metadata probes, RLS advisors and browser JWT behavior there.
3. Apply the approved migration to the approved environment, then create the dedicated `community-media` bucket through the Storage API or dashboard. If that bucket already exists, inspect it and its contents before changing it. It must have `public: false`, `fileSizeLimit: 52428800`, and `allowedMimeTypes: ['image/jpeg','image/png','image/webp','video/mp4','video/quicktime','video/webm']`. Use the Storage API `createBucket('community-media', { public: false, fileSizeLimit: 52428800, allowedMimeTypes: [...] })`; do not run SQL INSERT/UPDATE against Storage metadata tables. Keep all assessment buckets and objects separate.
4. The application uses the existing server-side `SUPABASE_SECRET_KEY` or `SUPABASE_SERVICE_ROLE_KEY` for guarded draft/publication/report/deletion transitions. This is never exposed in browser code. Verify that existing server configuration supplies it; this package grants no credentials. The browser uses its normal user JWT for a non-upsert direct upload to the reserved path. No new service or paid transcoding is required.
5. Deploy only after the parent review/release decision. Verify real separate accounts for active member, unauthenticated, expired and cross-owner scenarios; text/photo/video save and reload; cancellation, interrupted upload/retry; physical removal on author deletion; and iPhone playback. Local tests use disposable PGlite and mocked API/storage; they do not establish live Storage or codec behavior.

## Authorization and validation

Only current EMBER/IGNITE/PHOENIX members or existing explicit gifted members can see published posts or media. No free-community access is introduced. Owners retain visibility of their own draft/deleting rows after expiry solely for server-authorized cleanup. Browsers cannot insert/update/delete posts or reports, publish media, replace uploads, or delete Storage objects directly. Reports are written by the authenticated API after it checks a visible published post.

Each draft reserves exactly one `${author_id}/${post_id}/attachment.{jpg|png|webp|mp4|mov|webm}` path. Storage policies require that owned draft and current membership; restrictive policies prevent historical permissive policies from broadening this bucket. Other buckets retain their policies. Metadata MIME/size must match when present; Storage's preliminary INSERT probe can omit metadata. The private bucket enforces allowed MIME types and the 50 MiB ceiling, and the publish handler validates actual signature, MIME, exact bytes and the 10 MiB photo or 50 MiB video limit before making a post visible. Container validation cannot guarantee a browser supports the video's codec. HEIC/HEIF is rejected with JPEG export guidance; nothing is silently transcoded or reused from assessments.

## Cleanup and reports

Author deletion atomically marks the row `deleting`, empties its body, replaces its author display name and topic with neutral values, and clears its publication time before physical removal through the Storage API. The review SQL enforces this empty-content tombstone and blocks member reads/uploads of its media, including after a failed removal. Keep the tombstone and exact private media path even after successful removal so retries and late upload completion cannot resurrect a post ID. A failed removal remains inaccessible and retryable; a retry also scrubs an older tombstone before retrying Storage cleanup. Canceled or abandoned drafts, late writes racing cancellation, and old deleting tombstones need an operator reconciliation process: list old draft/deleting rows, apply the same content-scrubbing transition to abandoned drafts, call Storage `remove` for each exact reserved path, recheck after in-flight requests can no longer complete, and retain the tombstone. Do not directly delete from `storage.objects`; deleting metadata does not remove physical bytes. This package does not install a scheduled cleanup worker. Storage use can remain until reconciliation is performed.

Before deleting an auth account, the operator must remove all that author's media through Storage, verify absence including any late uploads, then remove their post rows. The author foreign key deliberately restricts account deletion until that work is done. Reports cascade with a removed post; reporter removal cascades only that reporter's reports. No assessment media is included in community cleanup.

Account-deletion integration remains blocked by a missing existing deletion flow in this checkout. `anastasis-mobile/app/profile.tsx` provides only an email link labeled “Request Account Deletion”; `components/account/AccountDashboard.tsx` directs privacy/deletion requests to support. The only `auth.admin.deleteUser` calls are in `app/api/auth/create-login/route.ts`, where they roll back a newly created login that failed invitation binding. Those calls are not member-account deletion and were not changed. No new account-management flow or unused account-deletion helper was added. The foreign-key restriction remains in place to prevent deleting an account while its private community media may still exist. A future approved account-deletion handler must stop new member writes, resolve in-flight uploads, scrub/remove all of that author's community media through Storage, verify absence, and then remove the author's community rows before deleting the auth user. This package does not claim that integration is operational.

Reports are persistent records with one report per reporter/post. They do not hide posts or notify a reviewer automatically. An authorized operator still needs to review the report table using existing administrative access and follow an agreed response process; no operational moderation queue or response guarantee is implied.
