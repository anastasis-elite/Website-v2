# Apple Health export review storage — prepared, not applied

`docs/sql/apple-health-export-review.sql` is an additive candidate. The local Supabase CLI is unavailable (`supabase --version`: command not found), so it has **not** been assigned a fabricated migration-history version. Native coordination must register these exact reviewed bytes under a new real migration version before a separately approved database apply. No database operation was performed by this package.

Prepared SQL SHA256: `c3801aa8d21a3da9b80ce6a276fb590edbe3f7f36003a656625f9af94489a166`.

This revised candidate supersedes `c2db4fe25c207d01f877ed5b55f8949f1c70983eafb2d218d68d64349dedd955`. **Do not apply those old SQL bytes.** The day reader now checks each stored instant’s actual local calendar date, retaining both occurrences when midnight repeats without assigning either to the preceding day. Ownership, capability checks, receipt identity, ordering and page limits remain unchanged.

The associated ZIP decoder correction permits at most 128 KiB of subsequent compressed input pushes without nonempty output; empty output callbacks do not reset the budget. It checks before reading another 1 KiB chunk. The chunk producing the last output can also contain up to one input chunk of unused suffix. A long padded suffix or pathological long sequence of empty DEFLATE blocks therefore fails closed as unsupported instead of growing decoder buffering. A maximal 65,535-byte stored DEFLATE block remains supported. Existing archive size, metadata and CRC checks remain in force. This conservative resource limit is not a claim that all decoder input was consumed or that the published file caps fit every device. Browser/iPhone capacity remains unverified.

Prerequisites: current `public.clients`, `auth.users`, authenticated/anon/service_role roles, and canonical `public.member_has_capability(text,text)` with the `healthRecords` capability. PostgreSQL must provide core `sha256(bytea)`, `trim_scale(numeric)` and the ordinary JSONB/timezone functions. No new extension/provider/credential is required. The candidate is transactional and fails if the table/functions already exist; reconcile a previous/uncertain application before retrying.

The dedicated `health_export_review_samples` table deliberately leaves `health_samples`, `daily_health_metrics`, native provider identities, integration states and sync cursors unchanged. Existing coaching/recovery/streak readers query those older tables, so exported heart rate and resting heart rate cannot silently enter them. The native metric constraint does not need expanding: raw export heart rate exists only in this isolated review schema. A future guidance feature must require a separately reviewed integration, not start reading this partition implicitly.

The new `health_export_private` schema **MUST remain unexposed in PostgREST/Data API configuration**. Native preflight must verify that dependency; this package changes no hosted schema exposure setting. Its owner-bound, RLS-protected `review_batches` table has only the invoker grants needed by the checked public operations. The client never calls it directly. It stores bounded per-batch counts and timestamps, not raw XML/record JSON or caller-supplied job metadata. The SHA256 batch identity uses the ordered normalized source-record identities plus selected day/timezone. An exact batch lock serializes receipt creation; sample insertion and first confirmation commit atomically. A retry reports actual current counts (usually 0 newly imported and N already present), while the original first-confirmation receipt remains immutable and visible after reload. Receipt history is explicitly per batch, not a whole-file total.

Authenticated reads/inserts require the current verified owner's `healthRecords` capability, in both RLS and invoker operations. Updates/deletes are not granted to members. User/client deletion cascades remove their imported rows; this adds no general health deletion UI. The identity trigger fixes provenance and derives SHA256 from metric, technical numeric value, absolute timestamps, creation timestamp and bounded source fields. Filename/import time/selected timezone are absent from identity. Identical indistinguishable export samples collapse; distinct timestamps, creation times, sources, versions or devices remain distinct. Native/export overlap cannot be proven from this identity and must remain disclosed as ambiguous.

Rollout: apply only after native SQL review and explicit production approval; deploy importer code after schema installation. If schema is absent, the API returns a truthful unavailable/error state; it does not fall back to native sample storage. Record exact registered SQL hash and version in the release receipt. Do not edit any previously applied migration or silently backfill old/native health data.

Rollback: hide/disable the importer route/UI first. Revoke the two RPC execution grants and INSERT on both review samples and private confirmations if urgent containment is needed. Preserve existing review rows and confirmations for owner export/support and retention review. A destructive DROP of review data requires separate authorization; no automatic DROP/rollback script is included. Native tables, readings, device status, cursors, and existing membership/history remain untouched.
