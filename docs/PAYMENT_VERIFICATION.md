# Payment setup and verification

The public pricing endpoint reads the configured Stripe Price and Product. It displays the actual amount, currency and billing interval. Monthly checkout requires a fixed monthly recurring price. Pay in full requires a one-time price with a positive integer `access_months` on the Price or Product; the variable name `EMBER_YEAR_PRICE` is retained for compatibility and is not evidence of an annual duration. Missing duration disables that checkout option without hiding the confirmed amount. New purchases retain the server-confirmed price and duration on the Stripe Checkout session, so later catalog replacement or deactivation does not alter that purchase. Legacy one-time sessions without an original confirmed duration require support review rather than an invented access period.

Before accepting payments, apply the additive payment migration, configure `STRIPE_WEBHOOK_SECRET`, and register `/api/webhooks/stripe` for `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.payment_succeeded`, and `invoice.payment_failed`. Configure the Stripe billing portal with the approved cancellation choices. The server derives portal ownership from the authenticated member's billing row, including canceled members; gifted memberships have no Stripe portal.

Configure `RESEND_API_KEY` and verify the existing `onboarding@anastasiselite.com` sender domain before guest checkout. A new purchaser receives their private, expiring login invitation at the receipt email; the browser confirmation never exposes this token. Confirm delivery in the isolated acceptance run, including provider failure and retry. Checkout refuses another purchase while the owned account has a nonterminal recurring subscription; manage that subscription through the account portal. Existing Stripe customers are reused when a canceled account purchases again. Conflicting guest purchases retain both billing identities for support reconciliation rather than hiding a recurring charge.

Use an isolated Supabase project or local test database and Stripe **test** keys and prices. Set `PAYMENT_TEST_DATABASE_ISOLATED=true` only after verifying that isolation. Preview deployments with live Stripe keys cannot create checkout sessions, fulfill payments or create billing portal sessions. Catalog reads remain available for read-only price confirmation. Checkout fails closed if the webhook secret or payment migration health function is missing.

For a real provider acceptance run, start the application against the isolated database, forward signed events using the Stripe CLI, and create a new QA customer email. Complete hosted Checkout using Stripe's documented `4242 4242 4242 4242` test card; verify the delivered webhook, `checkout_purchases` row, owner-bound client and billing records. Follow the returned browser confirmation through private login, profile and member baseline assessments, saved plan and nutrition guidance. Reload and sign in in a new session. Complete a workout/check-in and verify saved progress and updated dashboard. Follow support and paid billing management. Repeat with declined card, canceled checkout, pending asynchronous payment, and an existing customer's verified login.

Resend the same signed event and two different event IDs for the same session concurrently; confirm one client/purchase and unchanged access dates. Replay an older checkout after a renewal and deliver an older successful invoice after cancellation; confirm no resurrection or period extension. Test missing/cross-user checkout references, missing purchase cookie, invalid signatures, live/test mismatches, inactive access and direct authenticated changes to entitlement columns. IGNITE manual food persistence must be checked independently from barcode and image entry using a separate QA identity.

Repository behavior tests and local PostgreSQL migration tests exercise security and replay semantics. They do not establish a successful real Stripe charge, webhook delivery, Supabase authentication session, or configured billing portal. Those checks remain blocked until isolated provider credentials and the registered webhook are available. No production customer data or live charges are needed.
