# P0 daily-action source and production compatibility audit — 2026-10-13

This audit inspected application source and read-only catalogs in Supabase project `lcccpqgnpznhbtmkmytp`. It did not write production records, apply migrations, deploy, or exercise an authenticated browser account. Source repairs and disposable tests were subsequently prepared, as listed below. The matrix describes the production snapshot before approval: “Compatible” means metadata is present; it does **not** mean live save/reload passed. Hydration is covered by the separate root investigation.

The raw table/column/grant/RLS/policy/index/function/view evidence is preserved in [production inventory](p0-daily-action-production-inventory-2026-10-13.json). It contains no customer record values. Catalog queries used `pg_class`, `pg_attribute`, `pg_policies`, `pg_indexes`, `pg_constraint`, `pg_proc`, `has_table_privilege`, and `has_function_privilege`.

## Security and permission findings

1. **Audit access is deliberately unavailable to authenticated clients.** `recommendation_audit_logs` and `feature_consent_events` have RLS and own-user policies, but authenticated has no table privileges. The application calls request-client inserts/reads. Repair by authorized server operations or a constrained validated interface; don't grant unrestricted client audit access. [Audit helper](../lib/legal/logRecommendationAudit.ts) logs and swallows failure; program generation ignores insert results.

2. **Authenticated can modify sensitive client state through the Data API.** `clients` has table-wide UPDATE, an own-user policy with the same `WITH CHECK`, and no trigger. Catalog metadata imposes no column restriction on `program`, `access`, `verified_purchase`, subscription fields, or authorization-sensitive flags. This permits self-modification of the very `program` field used in tier policies. Review column privileges and trusted fulfillment paths before claiming EMBER restriction verification.

3. **Legacy meal-symptom policies bypass ownership.** “Authenticated users can read meal symptoms” uses SELECT `true`; “Authenticated users can insert meal symptoms” uses INSERT `true`. Both are PERMISSIVE. Own-row policies added later do not narrow these OR-combined permissions. Replace broad legacy policies or add a restrictive boundary requiring owner access through meal -> nutrition log.

4. **Some own-user policies do not validate the client association.** The old permissive `nutrition_logs` INSERT policy checks only `auth_user_id`; a later stricter policy is permissive too. Recovery, cycle, measurement, tasks, daily status/recommendation policies similarly rely mainly on auth/user ID. Member APIs validate client ownership, but direct database operations must enforce it independently. Add restrictive client-association checks while preserving records.

5. **Catalog and meal tier/privacy boundaries are restrictive.** `foods` has restrictive privacy and custom-food-tier policies; `food_nutrients` and serving options have restrictive parent-food visibility; `meal_entries` has a restrictive tier/ownership/food/serving/recurring validation boundary. These are not missing. All three nutrition views inspected have `security_invoker=true`.

6. **Assessment windows are inaccessible rather than publicly exposed.** RLS is disabled but authenticated has no table grants. Enable RLS and create SELECT/INSERT/UPDATE owner policies before granting access.

## EMBER contract in current application and production

[Capabilities](../lib/entitlements.ts) enable calendar, What's Next, workouts, hydration, basic recovery, progress/assessments/trends, and macro entry for EMBER. Meal logging, barcode, recurring/prelogging, photo estimation, recommended meals, directed/recommended recovery and posture analysis are false. The actual nutrition UI renders the macro form only for EMBER; production macro INSERT policy also permits only EMBER.

The older review document's “guidance-only” wording therefore does not describe the current macro-entry behavior. API capabilities currently enable `nutritionMacroEntry` for Ignite/Phoenix too, although their UI does not render the form and production denies those direct macro inserts. Resolve that discrepancy explicitly; don't broaden permissions automatically.

The general `clients.program` UPDATE exposure above means API denials alone cannot prove tier security. Required tests include direct EMBER calls to add-meal, custom-food, barcode/search/serving/recurring, and photo estimate; direct Data API food/meal inserts; cross-user records; attempts to mutate protected tier/client fields; and allowed EMBER macro save/reload if that remains the intended contract.

## Essential test gaps and observed failure modes

No authorized-account save/reload test was performed in this sub-audit. None of the compatible rows should be marked operational. Required test fixtures need a clearly authorized account and recorded pre/post state.

- Workout save and manual-set save cannot succeed against this snapshot because required RPCs/tables/columns are absent.
- Recurring commitment saves cannot succeed; missing commitments also block schedule create/move by design.
- Cycle settings fail on `answered_fields`; ovulation quick-log fails on `ovulation_day`; flow fails on burden columns before reaching absent tables.
- Measurements/assessments can commit legacy primary records and then return failure from absent derived/profile tables; repeated ordinary inserts can duplicate assessment/body sessions.
- EMBER macros can persist yet show stale nutrient totals on the nutrition page. The same macro data is added by the Home engine, creating cross-page disagreement.
- Sleep, daily check-in, manual sets, flow and assessments use multiple HTTP/database writes rather than a single encompassing transaction; equivalent replay tests must inspect partial persistence.
- Recovery and macro endpoints have no submitted identifier and append on each successful retry.
- Read errors are dropped in daily logic inputs, targetService, and advanced `safeQuery` helpers. Recommendation and execution persistence errors naming their table are suppressed. Successful rendering/HTTP 200 can conceal absent inputs or failed derived writes.
- Phoenix photo estimation remains unavailable by application design (501); keep it an explicit outstanding failure.
